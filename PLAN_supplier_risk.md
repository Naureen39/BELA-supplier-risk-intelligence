# Supplier and Counterparty Risk Intelligence Platform

Implementation plan using BELA and BLINK for entity linking and entity resolution.

Working product name: `BRAND_NAME` (default "Provenance Risk"; run a trademark check before any public launch).
Team: 1 to 2 full-stack engineers with ML experience. Duration: about 16 weeks.

## 1. Writing and engineering conventions (mandatory)

- Use a professional, neutral tone in every artifact: code comments, commit messages, docs, issue titles, UI copy, marketing copy. No slang, jokes, emojis, or hype wording.
- Never mention any AI assistant, chatbot, or AI vendor tool by name in code, comments, docs, commit messages, or UI copy. No "generated by" notes.
- Never use the em dash character (Unicode U+2014) anywhere. Use a colon, comma, parentheses, or a plain hyphen. Add a CI step that fails the build if U+2014 appears in any tracked text file.
- Every claim in the UI or marketing pages must be backed by a measurement produced in this repository or by a cited public source. No invented customers, customer logos, testimonials, awards, press mentions, or certifications. Scenario cards must be labeled "Illustrative scenario".
- Never state that a company broke a law or caused an incident. State what a named public record says, with the source, the record date, and a link. Distinguish allegations, citations, and recalls from findings of fault.
- Conventional Commits, pull request template, architecture decision records in `docs/adr/`.
- Python: type hints everywhere, `ruff`, `mypy` (strict on core packages), `pytest`. TypeScript: strict mode, ESLint, Prettier. Backend core logic coverage of at least 80 percent.

## 2. Scope and constraints

**Product.** A web platform where procurement, third-party risk, insurance, lending, and research teams upload a messy list of suppliers or counterparties and receive a continuously updated risk view. Entity resolution connects each supplier to a canonical company, its parents, and its subsidiaries, then attaches news events and regulator records (recalls, workplace safety, environmental enforcement) to the right company, including events recorded under a different name or at a subsidiary.

**In scope:** supplier upload and resolution, human review of uncertain matches, event ingestion and classification, corporate family graph, risk scoring with roll-up, alerts and monitoring, reports, operational and portfolio analytics, platform revenue analytics, authentication and authorization, marketing website.

**Out of scope:** real payments, real customer data, legal determinations, credit ratings, production compliance certification.

**Constraints**
- Free and open-source tooling only. Any LLM runs locally and is a 3B to 4B model from Hugging Face.
- Structured regulator and filing data is mostly US sources (SEC, EPA, OSHA, NHTSA, CPSC, FDA). News can be global. State this limit on the Methodology page.
- Tenants, subscriptions, invoices, revenue, and the demo supplier portfolios are synthetic. The UI must show a visible "Demo data" label wherever they appear. Demo portfolios use real public company names but do not represent real commercial relationships and must say so.
- Results are leads for human review, not determinations. Show this disclaimer on every supplier view and report.
- Respect source terms: SEC fair access rules (declared User-Agent, rate limits), robots.txt for news pages, publisher copyright (store snippets only).

**Three linking problems (the core of the project)**

| Problem | Input | Target | Method |
|---|---|---|---|
| A. Structured resolution | Regulator facility or firm records (name, city, state, program), EDGAR subsidiary names | Canonical company | Blocking, bge-m3 retrieval, Splink score, fine-tuned BLINK bi-encoder and cross-encoder |
| B. News linking | Company mentions in article text | Canonical company | BELA detection and linking to Wikidata, mapped to canonical companies through identifiers, BLINK custom-KB fallback for unlinked mentions |
| C. Supplier list resolution | User-uploaded names with optional address, state, country, website, identifiers | Canonical company | Same engine as A with user attributes, confidence routing, human review |

**Canonical company model**
- `companies` (id, canonical name, legal form, CIK, LEI, Wikidata QID, tickers, SIC code, state of incorporation, headquarters, public flag, status)
- `company_aliases` (alias, type: legal, former, doing-business-as, subsidiary, abbreviation; normalized form; source)
- `company_relationships` (parent, child, type, ownership share, source: GLEIF, EDGAR Exhibit 21, Wikidata, as-of date)
- `facilities` (registry ID, name, address, coordinates, industry code, linked company, link confidence)

**Pipeline rules**
- Resolution results are stored with method, score, route, and every candidate considered, so analysts can inspect why a match was made.
- Mentions or records that cannot be resolved stay as unresolved (NIL) and are never silently attached to a company.
- Article content is untrusted input for the local LLM. See section 10.

### 5.3 Dataset build order and checks

1. `make data` runs all download scripts, writes manifest hashes, and prints row counts.
2. `make etl` produces `data/processed/*.parquet` and loads PostgreSQL.
3. Data quality tests (pandera and SQL assertions): no null names, valid state codes, no duplicate source keys, alias counts, identifier coverage per source (CIK, LEI, QID), event date sanity, vector dimension equals 1024.
4. `make training-data` generates synthetic training pairs (section 5.4).
5. `make seed` loads `data/seed/` (demo tenant, users, demo supplier portfolio, 90 days of processed events and alerts) so a fresh clone shows a populated product.

### 5.4 Training data and synthetic business data

**Synthetic training pairs for BLINK (`data/training/`)**
- Entity catalog: one record per canonical company with a title (canonical name) and a description text built as: "Legal name, aliases, industry (SIC and Wikidata industry), headquarters city and state, public or private, parent company, tickers".
- Mention records in BLINK's training format (context left, mention, context right, entity label ID; confirm the exact format in the repository's training documentation). For structured records the context is the facility or firm record text (city, state, program), and the mention is the raw name.
- Perturbations applied to canonical names and aliases: legal suffix changes (INC, INC., INCORPORATED, LLC, L.L.C., CORP, CORPORATION), leading "THE", punctuation and case, abbreviations (INTL, MFG, CO, GRP), keyboard-adjacent typos, token order swaps, truncation, location suffixes ("OF OHIO"), plant or site suffixes ("PLANT 3"), doing-business-as names, trailing codes.
- Hard negatives: same name in a different state, similar names (for example food versus food service), parent versus subsidiary, unrelated companies sharing a word.
- Splits by company (not by record) into train, dev, and test, so evaluation measures generalization to unseen companies. Never use gold-set companies in training.

**Synthetic business dataset**

Generated by `data/scripts/generate_demo_business_data.py` with a fixed random seed (42). History window: 2023-11-01 to 2026-10-31 (36 months). Output goes to `data/synthetic/*.csv` and is loaded into PostgreSQL. Tenant names must be clearly fictional (neutral word pairs plus generic suffixes) and must not copy real institutions.

| File | Content |
|---|---|
| `tenants.csv` | id, name, industry, region, country, created_at, churned_at, acquisition_channel |
| `subscriptions.csv` | tenant_id, plan, billing_cycle, price, start, end, change_reason |
| `invoices.csv` and `invoice_lines.csv` | invoice per month per tenant, line types: subscription, overage, credit; status: paid, open, overdue |
| `usage_daily.csv` | tenant_id, date, monitored_suppliers, resolutions, events_matched, alerts, api_calls |
| `portfolio_stats_daily.csv` | tenant_id, date, risk_index, suppliers_by_level, auto_resolved, reviewed, unresolved, median_review_minutes |
| `platform_stats_daily.csv` | date, p50_latency_ms, p95_latency_ms, false_links_per_1000, review_rate |
| `marketing_spend.csv` | month, channel, spend |
| `business_events.csv` | date, label (pricing change, product launch, new data source) used as chart annotations |

Generation rules (tune to land at an ending ARR envelope of roughly 5 to 9 million USD):
- New logos per month follow a Poisson process whose rate grows from about 2 to about 7. Plan mix at signup: Starter 50 percent, Professional 35 percent, Enterprise 15 percent.
- Illustrative list prices: Starter 499 USD per month (up to 250 monitored suppliers), Professional 1,999 USD per month (up to 2,500), Enterprise 8,000 to 25,000 USD per month (lognormal, larger portfolios). 40 percent annual billing with a 10 percent discount. Overage billed per 100 monitored suppliers above the plan limit.
- Monthly logo churn: Starter 3.0 percent, Professional 1.5 percent, Enterprise 0.6 percent. Monthly expansion probability about 4 percent with a 10 to 40 percent increase. Occasional contraction.
- Regions: North America 60, EMEA 25, APAC 12, LATAM 3 percent. Industries: manufacturing, automotive, food and beverage, consumer products, healthcare and life sciences, logistics, insurance, banking.
- Usage: portfolios grow over time, weekday seasonality, quarter-end review spikes, a lift after a new data source event, a one-time price increase for new customers at month 20.
- False link rate and review rate trend down over time (reflecting model improvements); latency trends down after an optimization event.
- Acceptance: two runs yield identical files; monthly MRR is continuous and non-negative; invoice totals reconcile to subscriptions plus overage.

**Demo supplier portfolios (`data/synthetic/portfolios/`)**
- Generated by `generate_demo_portfolios.py`. ## 6. Phase plan

Each phase ends with a demo, a tagged release, and all exit criteria met.

### Phase 0: Foundations and technical spikes (week 1)

**Goal:** remove technical risk before building features.

Tasks
1. Create the monorepo, pre-commit hooks, CI (lint, type check, unit tests, gitleaks, pip-audit, npm audit, U+2014 check), PR template, ADR template.
2. Write `infra/docker-compose.yml` with services: `postgres` (pgvector image), `valkey`, `api`, `worker`, `web`, `nel`, `blink`, `llm`, `caddy`, `mailpit`. Health checks on all. Secrets through git-ignored `.env` files and an `.env.example`.
3. **Spike A, BELA.** Create a GPU environment. Try the official repository (`facebookresearch/BELA`, MIT) and the community wrapper `multiel` (`pip install multiel`), which loads checkpoints (`wiki`, `aida`, `mewsli`, `e2e`) from the Hugging Face repo `wannaphong/BELA`. Review and pin the wrapper, vendor the code if needed. Run 50 English sentences about companies (plant fires, recalls, lawsuits) plus 10 in other languages. Record: VRAM, passages per second, default thresholds (mention 0.2, linking 0.4), whether top-k candidates and scores can be returned (patch inference to return the top 10 if not), what entity index ships with the checkpoint, and how often company mentions link to the correct Wikidata company. Output ADR-001: use the bundled index or rebuild an index for the company subset by encoding "title plus description" with BELA's entity encoder.
4. **Spike B, BLINK custom knowledge base.** The upstream repository is archived and targets older Python and PyTorch. Build a pinned, isolated container. Run `download_blink_models.sh` and confirm the pretrained bi-encoder and cross-encoder run. Then train on a toy custom catalog of 1,000 companies with synthetic mentions to confirm the training scripts for both models work, record the data format, GPU memory, and time per epoch. If the large encoder does not fit in memory, test gradient accumulation, fp16, and a base-size encoder, and record the accuracy tradeoff. Confirm the cross-encoder can score arbitrary (context, candidate title plus description) pairs. Input uses `[ENT_START]` and `[ENT_END]` markers around the mention. Output ADR-002.
5. **Spike C, local LLM.** Run `llama-server` with Qwen3-4B-Instruct-2507 Q4_K_M (official or reputable GGUF build, verify checksum and license, or convert locally). Test JSON-schema constrained output on 20 prompts (event type and severity labeling, candidate choice). Record tokens per second and VRAM.
6. **Spike D, embeddings and record linkage.** Encode 200 thousand company names with bge-m3, index in pgvector with HNSW (`m=16`, `ef_construction=64`), measure recall at 10 and latency. Run a Splink model on a 5,000 record sample of regulator names against EDGAR names to measure a baseline.

Deliverables: running compose stack, four spike reports, ADR-001 and ADR-002, hardware budget, go or no-go note per component.
Exit: all services start with `make up`; BELA links a company mention in a sentence; BLINK fine-tuning runs end to end on the toy set; vector search and Splink baselines produce numbers.

### Phase 3: Entity resolution and linking engine (weeks 4 to 7)

This is the core of the project.

**Services**
- `services/nel`: loads BELA once, exposes `POST /v1/link` with input `[{id, text, lang}]` and output per mention: `start`, `end`, `surface`, `qid`, `md_score`, `el_score`, `candidates[{qid, score}]` (top 10). Also `POST /v1/embed` for bge-m3. Batching, fp16, backpressure, `/health`, `/metrics`.
- `services/blink`: custom-KB retrieval and re-ranking. `POST /v1/retrieve` (mention, context) returns top-k companies from a FAISS index over the fine-tuned bi-encoder's company embeddings. `POST /v1/rerank` scores (context, candidate) pairs with the fine-tuned cross-encoder. Index rebuild job runs when the company table changes.
- `services/llm`: llama.cpp server, chat-completions HTTP endpoint on an internal network only. A thin client enforces JSON-schema output, temperature 0, token limits, timeouts.

**Training (BLINK, `make train`)**
1. Generate training data (section 5.4). Initialize from the pretrained BLINK bi-encoder and cross-encoder.
2. Train the bi-encoder with in-batch and mined hard negatives. Mine negatives from its own top-k errors and retrain once.
3. Train the cross-encoder on the bi-encoder's top-k candidates.
4. Select checkpoints on the dev split. Report on the held-out company test split and on the gold sets.
5. Record training configuration, data hashes, and metrics in `docs/model_card.md`.

**Resolution pipeline for structured records and uploaded suppliers (problems A and C)**
1. Normalize the name and parse the address.
2. Exact identifier match (CIK, LEI, ticker, website domain) accepts immediately.
3. Candidate generation: union of trigram search, bge-m3 vector search, and BLINK bi-encoder retrieval, with state and country used as soft blocking.
4. Scoring: Splink match weight, fuzzy features, state and city agreement, industry code agreement, BLINK cross-encoder score. A small logistic model combines them, trained on the dev split.
5. Routing (initial values, calibrate on gold): accept at calibrated probability of 0.90 or higher with a clear margin over the runner-up; send to human review between 0.50 and 0.90 or when the margin is small; unresolved below 0.50.
6. Parent roll-up uses `company_relationships`. Store the path so the UI can show why an event reaches a supplier.

**News linking pipeline (problem B)**
1. Chunk articles to the encoder's maximum length at sentence boundaries with small overlap. Pre-filter articles with an event-topic classifier (bge-m3 plus keyword rules) to control cost, and measure recall loss on the gold set.
2. BELA mention detection and linking. Map linked QIDs to canonical companies through stored identifiers (LEI, CIK, ticker) and the QID map.
3. Routing: accept confident links to companies; for mentions BELA leaves unlinked or links to non-company entities, call BLINK `retrieve` and `rerank` over the company catalog using sentence context.
4. Remaining ambiguous cases go to the local LLM with five candidates and descriptions, returning `{choice, confidence, reason}`. Combine scores with a calibrated model. Store all candidates and scores in `link_candidates` for the transparency panel.
5. Type filter: keep only organizations that are companies.
6. Calibration: isotonic or Platt calibration per route, reliability plots.

**Evaluation harness (`make eval`)**
- Systems: RapidFuzz with state blocking; Splink only; bge-m3 retrieval only; BELA only (news); BLINK pretrained on Wikipedia knowledge (zero-shot, news); BLINK fine-tuned custom-KB; full hybrid.
- Data: structured gold, news gold, held-out synthetic test split, optional Mewsli-X sanity check.
- Metrics: recall at 1, 5, 10 for candidate retrieval; accuracy at 1; precision and recall at the chosen threshold and a full precision-recall curve; NIL detection F1; review rate (share routed to humans); parent roll-up accuracy; throughput (records and passages per second); p50 and p95 latency; false links per 1,000 records.
- Output `docs/eval/report.md`, a CSV per run, and `public/metrics.json` for the website.
- Initial targets (confirm or revise with evidence): hybrid reaches at least 95 percent precision at 80 percent recall on the structured gold set; at least 50 percent fewer false links than RapidFuzz at equal recall; fine-tuned BLINK improves accuracy at 1 over the pretrained model by at least 20 points on structured records; review rate of at most 20 percent; BELA stage at least 20 passages per second on the target GPU.

Deliverables: three services, trained checkpoints, pipeline library, versioned thresholds, evaluation report, model card with data, intended use, limits, failure modes.
Exit: evaluation report committed; thresholds frozen as `resolution_config_v1`; 10,000 record and 10,000 article throughput tests pass.

### Phase 4: Event pipeline and risk scoring (weeks 6 to 8)

Tasks
1. **Regulator normalizers:** convert EPA, OSHA, NHTSA, CPSC, and FDA records into the common `events` schema with source IDs for idempotent reloads. Map fields to event type and severity using a versioned rules table in config (for example: OSHA penalty and violation type, EPA significant violation flag and penalty amount, FDA recall class, CPSC hazard type, NHTSA units affected). Confirm field names in each data dictionary.
2. **News event classification:** the local LLM labels the evidence sentence with an event type and severity (1 to 4) using a JSON schema. Event types: workplace safety, environmental, product safety recall, regulatory enforcement, litigation, financial distress, operational disruption (fire, explosion, closure, strike, shortage), cyber incident, governance and fraud, other, none. Article text is wrapped in delimiters and treated as data only.
3. **Event deduplication:** cluster the same incident across news articles and regulator records (same company, type, location, time window, embedding similarity) into one event with multiple sources.
4. **Attach events to companies:** run the resolution pipeline for each event entity and store method and score. Regulator events that resolve with low confidence go to a platform review queue and do not appear in tenant views.
5. **Risk score** (configurable, versioned, editable by tenant admins within bounds):
   - `event_impact = severity_weight * recency_decay * link_confidence * relation_weight * source_reliability`
   - Default severity weights for levels 1 to 4: 0.10, 0.25, 0.45, 0.60. Recency half-life: 180 days for regulator and recall events, 30 days for news incidents. Relation weight: direct 1.0, subsidiary event to its parent 0.7, parent event to its subsidiary 0.5, sibling 0.2, depth limited to 2. Source reliability: regulator 1.0, news 0.7.
   - `supplier_risk = 100 * (1 - product over events of (1 - min(event_impact, 0.6)))`
   - Levels: critical at 70 or above, high 50 to 69, medium 30 to 49, low below 30. Sub-scores per category. Show every component in the UI.
6. **Monitoring:** scheduled tasks recompute scores when new events or company changes arrive and create alerts for threshold crossings and for new high severity events, de-duplicated per supplier and event.
7. **Evaluation of event labeling:** score event type and severity labeling on 200 gold sentences, and record per-class precision and recall.

Deliverables: normalizers for five regulators, news event classifier, dedup logic, risk scoring library with tests, rules and weights in versioned config.
Exit: end-to-end test: ingest fixture regulator records and a fixture article, events attach to the correct companies including a parent roll-up case, score changes, alert is created.

## 10. Security, authentication, and authorization specification

**Authentication**
- Passwords: Argon2id with tuned parameters, minimum 12 characters, zxcvbn strength check, common password rejection, no composition rules that reduce entropy.
- Login protection: per-account and per-IP rate limits, progressive delay, temporary lockout, generic error messages, audit entries for failures.
- MFA: TOTP (pyotp) with QR enrollment, 10 single-use recovery codes stored hashed. Mandatory for platform admin and tenant admin roles.
- Tokens: short-lived access JWT (10 to 15 minutes, EdDSA) in an httpOnly, Secure, SameSite=Strict cookie. Refresh tokens are opaque random values stored hashed, rotated on every use, with reuse detection that revokes the whole session family. Absolute session lifetime and idle timeout configurable.
- CSRF: double-submit token for state-changing requests; the web app proxies `/api` to keep a single origin.
- Password reset: single-use, time-limited, hashed tokens; no account enumeration.
- API keys: random prefix plus secret, stored hashed, shown once, scoped to permissions and tenant, with expiry and last-used tracking.

**Authorization (RBAC with tenant scoping)**

| Permission | viewer | analyst | manager | tenant admin | finance analyst | platform admin |
|---|---|---|---|---|---|---|
| View suppliers, events, alerts, graph | yes | yes | yes | yes | no | yes |
| Upload suppliers, review resolutions | no | yes | yes | yes | no | yes |
| Acknowledge and dismiss alerts | no | yes | yes | yes | no | yes |
| Manage alert rules, view analytics, create reports | no | no | yes | yes | no | yes |
| Manage users, API keys, risk config | no | no | no | yes | no | yes |
| View audit log (tenant) | no | no | no | yes | no | yes |
| View platform revenue | no | no | no | no | yes | yes |
| Manage tenants, platform settings, platform review queue | no | no | no | no | no | yes |

Enforce on the server with dependency-injected permission checks and PostgreSQL Row Level Security. The frontend hides unavailable actions but never relies on hiding for protection. Add automated tests for every role against every endpoint group and for cross-tenant access attempts.

**Data protection**
- TLS 1.2 or higher everywhere with HSTS. Encrypted disk volumes for the database host. Column-level encryption with pgcrypto for tenant-supplied supplier identifiers (tax IDs, account numbers if present in uploads). Keys loaded from environment secrets, never committed.
- Tenant supplier lists are confidential business data: never used to train or evaluate models without an explicit tenant setting, never visible to other tenants, deleted on request. Reviewer feedback used for training is stored only when the tenant opts in, and stripped of tenant identifiers.
- Data minimization: store snippets and extracted mentions, not full article text. Retention settings per tenant with a scheduled purge job.
- Logs must never contain passwords, tokens, or supplier identifiers. Structured logs with request IDs.
- Tamper-evident audit log: append-only table with a hash chain, verification job, no update or delete permission for the application role.
- Upload safety: CSV size and row limits, formula injection protection on exports (prefix cells that begin with =, +, -, @), content type checks.
- Security headers: strict Content Security Policy, X-Content-Type-Options, frame protections, Referrer-Policy, Permissions-Policy. CORS disabled by default (same-origin).
- Dependency and image hygiene: pinned versions, lock files, Trivy and gitleaks in CI, non-root containers, read-only file systems where possible, internal-only networks for the database, queue, and model services.

**LLM and pipeline safety**
- Treat all article text as untrusted. Wrap it in explicit delimiters, instruct the model to treat it as data, constrain output with a JSON schema, disable tools and network access for the model, cap token counts, and validate outputs before storage.
- The LLM never makes the final resolution or risk decision alone. Its outputs are inputs to the score and are always shown with the evidence.
- Record model name, version, prompt version, and configuration version on every stored decision.
- Fetcher safety: block private IP ranges (SSRF protection), enforce response size and time limits, sanitize extracted text, honor robots.txt.

**Responsible use**
- Disclaimers on supplier views and reports; wording on events always cites the record, its date, and its source.
- A visible correction process for wrong links and outdated records, with response tracking.
- Error analysis (similar company names, common words in names, parent and subsidiary confusion, non-US coverage gaps) documented in `/methodology` and `docs/model_card.md`.
